# Gap plan, 2026-11-04: drivers, local-model speed, consistent voice

Review of everything in this repository, the unshipped worktrees and the live phone (read-only probes,
2026-11-04), then a prioritised plan. Items marked **phone** need the device; everything else is done or
can be done on a computer. Status words: **working** (used daily), **partial** (works with gaps),
**missing**, **blocked** (no open path known).

## 0. Read first

- **This S22 is the Exynos model**: SM-S901B/DS, Exynos 2200 (`s5e9925`, board `r0s`). Plans written for the
  Snapdragon S22 (SM8450 "waipio": Adreno/freedreno, WCN6855/ath11k, pmic-glink, AudioReach, CAMSS/CCI,
  Hexagon/QNN) do not apply. Section 1 maps every block to the part this phone really has.
- **It is not mainline Linux.** The kernel is the LineageOS/Samsung vendor kernel 5.10.260 (source commit
  `4e5c5ad7`), with the 325 vendor modules loaded by AOSP first-stage init, then our guardian as PID 1, a
  native Alpine root and an Arch userland. Almost every driver therefore already exists as a vendor module;
  the gaps are missing **userspace** (the Android HALs we replace), firmware staging, and a few kernel bugs.
  `kernel/` and `dt/` in this repo are empty on purpose: the device tree is Samsung's, patches live in
  `tools/hardware/*.patch`, and the 2.4 GB kernel checkout stays local (`lineage/`, ignored).
- **The 11 "unshipped" worktrees are shipped.** Every commit in `~/wt/s22-{buttons,campreview,devapi,guide,
  guidepush,haptics,merge,phase0,shell2,shellport,voice}` is on `main` under a rewritten hash (the 10-22
  history rewrite). Four are tree-identical to their `main` counterpart; the rest have identical patches
  except two: the `main` copies are the privacy-redacted network evidence and a rebased fastshell config.
  Nothing should be merged from them (section 5).
- **The phone's agent currently runs on the local model.** Probe 2026-11-04: OpenUnum's default model on the
  phone is the local Gemma-4 E2B, so voice and card turns run on two threads of the phone's A710 cores; the
  most recent local turn waited 98 s for its first token, most likely because the lean prompt's sliding
  history window defeats the prefix cache. Section 2.2.

### 2.2 Why the local model felt slow on 11-04

The probe found the local model loaded for 5 days 14 hours (4.0 GB resident) because the phone's
OpenUnum uses it as its default, so requests keep arriving and the 10-minute idle unload never fires. The
proxy log shows a controller turn (the lean system prompt + 6 history messages, 4.7 KB of history) that
waited **98 s for its first token**.

Most likely cause, from the code: the lean profile (`lean_request` in `s22-llama-ondemand`) keeps a
**sliding window** of the last 6 messages and clips a message to 600 characters once it is older than the
current question. Once a chat has more than 6 messages, the text right after the byte-stable system
prompt therefore changes on every turn, and llama.cpp can reuse only the ~700-token system part of its
cache: the whole history is prefilled again at 20-32 tok/s. The daily prefix slot was not saved either
(`slot: false`: the warm-up waits for 60 quiet seconds that never come), and OpenUnum's own side requests
(no tools, another system prompt) share the single slot (`-np 1`) and can evict even the system part.
The proxy now logs llama-server's own `cache_n` / `prompt_n` for every request, which settles this on the
first turn after the update.

Fixes, in order of value (all **phone**; acceptance: turns 2-5 of one conversation reach their first token
in under 15 s, `prompt_n` well below the history size in `ondemand.jsonl`):
1. **Owner decision:** put the phone's default back to the cloud model with the local model as the
   offline fallback (the design), or keep local by choice. Either way, give it a non-empty fallback list.
2. Make the lean history append-only: clip each message once, when it enters the window, and keep it
   byte-identical afterwards; drop old messages in blocks (for example, let the window grow to 12 and then
   cut to 6) so a full re-prefill happens every few turns instead of every turn. Check first how many
   messages OpenUnum itself sends: if its own window slides, the proxy cannot hold the prefix stable.
3. `-np 2` with the same total `-c 16384`, so side requests land in the second slot (same KV memory; the
   lean controller prompt is ~3k tokens, well under 8k per slot); save the controller slot after a
   completed turn instead of only after 60 quiet seconds.
4. Measure the prefill-thread knob and the KleidiAI build (built today, below) with `s22-llm-bench`.

### 2.3 Why the voice was inconsistent (root cause)

Owner, 10-22: "stop switching between voices". Found in this review:
1. **The engine was chosen per chunk, not per answer.** Every answer chunk was a separate render that tried
   the rig with the first chunk's tight deadlines (first audio in 2 s, whole clause in 3 s + 0.12 s per
   character). Under the main model's GPU load the rig voice runs at RTF 1.3-2.1, so a later chunk fell back
   to the phone's Piper copy in mid-answer, and the 60-second "rig down" marker then kept the next chunks
   there. **19 of the last 50 renders on the phone were the fallback voice** (probe 11-04).
2. **Fillers only existed in the rig voice**, so a filler and the answer after it differed whenever the
   rig was down.
3. **Engines start and end with different amounts of silence** (VoxCPM, Piper and espeak differ by up to
   ~0.4 s), so the pause between chunks changed with the engine.
4. English in the offline fallback is spoken by the Greek-trained distilled voice (only partly
   intelligible); kept on purpose (one voice), `S22_TTS_OFFLINE_EN=supertonic` trades voice for clarity.
5. Every chunk is played by a fresh `s22-say` that applies the mixer route, raises the amps, plays, then
   resets: 0.3-0.6 s between chunks and possible amp ramps. Not changed yet (item P1b).

Loudness itself was already fixed on 10-22 (every path at -16 LUFS, peak -2 dBFS).

**Built today (commit `voice: one voice per answer…`):** the first chunk's voice speaks the whole answer;
later rig chunks get the playback time left on the previous chunk as extra deadline, and a rig failure
switches the rest of the answer once, never back (`S22_SAY_VOICE=phone`, logged as `voices` /
`voice_switch_at` in `assistant.jsonl`); a filler bank in the phone voice (`s22-render-fillers --engine
el-antonis`) is used while the rig is down; every render is trimmed to a fixed 60 ms lead / 180 ms tail
before the loudness measurement (`S22_SPEECH_PAD`).

(`/srv/s22/state/rigvoice.json` `{"enabled": false}`) fillers come from `voice-fillers-el-antonis`; a phone-mic
loopback of a 3-chunk answer shows pauses of 0.25-0.6 s between chunks (`tools/hardware/audio-speech-loopback.sh`).
**P1b** one playback stream per answer (route and amps set once, chunks queued into one `aplay` with
silence between them): needs the phone, opt-in first; risk medium (Calliope faults recover with
`audio-abox-recover.sh`). **P1c** stream the first rig chunk to the speaker while it renders when the measured
RTF is below 0.8 (render 4.4-4.8 s → under 1 s at idle).

**P2 Local model speed (phone).** Section 2.2 items 1-3, then on the phone:
`python3 tools/model-bench/s22-llm-bench.py run` (stage `builds/llama-kleidi-cpu/bin/llama-{server,bench}` as

and apply its one-line setting (`/srv/s22/state/llama-ondemand/threads-batch`). Acceptance: turn time to
first token (the `turn` workload) at least 25 % lower than `cool2`, peak below 66 C, decode not slower,
same greedy answer hash (or a quality check if it differs). References: llama.cpp `--threads-batch`,
`GGML_CPU_KLEIDIAI`; the 10-11 benchmark brief.

**P3 Battery (built; phone).** `sh tools/hardware/power/install-charge-limit.sh`, then `s22-charge-limit set
85` (owner OK). Acceptance: on USB the status turns "Not charging" at 85 %, charging resumes at 83 %,
the limit survives `s22-reboot recovery` (the service re-applies it). Reference:
`drivers/battery/common/sb_full_soc.c` (`batt_full_capacity`).

**P4 Calls (phone + owner).** a) Dial and hang up one call to the allowlisted number through `s22-phoned`
(signalling only, no audio route): confirm CALL_STATUS transitions and whether the network gives 2G CS
voice at all (no VoLTE). b) Generate in-call routes from the stock `mixer_paths.xml` (the `gen-mixer-batches.py`
approach used for media) and find the CP↔ABOX voice path the stock HAL uses (the 10-21 Calliope finding
came from disassembling the stock audio library; do the same for voice). c) Proximity: screen off at the
ear. Acceptance: a two-way call to the owner where both sides hear each other, logged in the device audit.
References: libsamsung-ipc `ipc_call_*`, stock `mixer_paths.xml`, `RECON.md`. Effort L.

**P5 Bluetooth pairing and audio (phone + owner).** `bluetoothd` in the chroot on hci0, pair the owner's
headset, A2DP sink through bluez-alsa into the ABOX graph (or PipeWire). Acceptance: the agent speaks
through the headset; reconnect after `s22-reboot recovery`. References: BlueZ, bluez-alsa;
`docs/BT_AUDIO_NATIVE.md` (`a2dpcom.bin` is only for the offload path).

**P6 Camera (phone).** a) Torch tool: `/sys/class/leds/torch-sec1/brightness` (0-15) as an `s22d`

**P7 Sensors (phone).** Auto-rotate from the hub's `autorotation` IIO device into fastshell; light → backlight;

**P8 Kernel candidate (phone + owner).** Build a RECOVERY image = the running HCI-fix kernel + the

**P9 GPS (phone, outdoors).** `gnss-rt.sh probe --seconds 900` outside, then time/position injection, a

**P10 Cold power-on (phone + owner present).** A boot path that reaches Linux from a normal power-on
