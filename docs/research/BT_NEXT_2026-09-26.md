## Bridge lifecycle change

The embedded bridge previously opened a second `AF_BLUETOOTH` raw socket after
its 20-second bridge interval to print adapter statistics. It did so even when
the bridge had failed or received a stop signal. The bridge no longer opens
that socket. A successful `HCIUARTGETDEVICE` now supplies the registration
receipt (`bridge_registered_hci=<index>`); in the pinned
`drivers/bluetooth/hci_ldisc.c`, this ioctl returns `hu->hdev->id` only when
`HCI_UART_REGISTERED` is set, and otherwise returns `-EUNATCH`.

The bridge records ownership only after `TIOCSETD(N_HCI)` succeeds. A failed
initial line-discipline ioctl has no detach attempt; failures in
`HCIUARTSETPROTO` or `HCIUARTGETDEVICE` reach one shared detach path. Ownership
is consumed before the detach ioctl, so a failed detach is reported and never
retried. The original attach/bridge errno is restored after cleanup; a detach
failure changes an otherwise successful result to failure and is separately
reported. The standalone CLI bridge has a distinct one-time TTY restoration
path; it does not claim HCI attachment. This does not turn a host registration
receipt into phone or controller acceptance.

The runner's default and `--execute`-without-separate-ack paths remain closed.
Its gate reflects the consumed one-shot socket check and requires exact
RECOVERY identity/readback, independent review of attach/detach/poweroff, and
separate explicit authorization. It refuses optimized host Python. The
configured binary and staging destination point to this milestone's unique
paths.
