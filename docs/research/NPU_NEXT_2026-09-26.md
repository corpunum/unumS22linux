# NPU publication lifetime: host evidence and remaining blocker — 2026-09-26

## Finding

The current lifecycle candidate does not free its stack waiter while the
protocol publisher owns a publication lease: timeout cancellation marks the
waiter canceled, then waits without a timeout for `publish_done` before the
caller unlinks the waiter and returns. That is the safe lifetime side of the
tradeoff, but it is not a liveness fix. A stalled synchronous mailbox post can
hold the `POWER_NOTIFY` caller, its session-manager mutex, and the boot/close
path indefinitely. The 12-second firmware-response wait does not bound this
drain.

No heap-only detach was accepted. A detached request would need independently
reviewed ownership of both the vertex/device lifetime and every selected
hardware-device reference, including exact `hids`, partial-acquisition unwind,
close/error ordering, and a finite cap on requests retained behind a publisher
that never returns. It would still need to account for a successful late
`POWER_ON` after caller timeout: the source does not prove that a later
compensating `POWER_OFF` prevents the late transition from leaving hardware on.
No device or module lifetime pinning design is implemented here.

## Exact source path reviewed

The read-only source tree was at
`/home/corpunum/s22-linux/lineage/android_kernel_samsung_s5e9925`, exactly
`4e5c5ad7d950e4de0688b5663965f2075654b2ad`; it remained clean. The candidate
patch is `tools/hardware/npu-session-lifecycle-fix.patch` in this worker repo,
and `git apply --check` accepted it against that pinned tree. The patch itself
was not changed by this work.

In the pinned baseline, `npu_sessionmgr_regID()` assigns
`session->global_lock = &sessionmgr->mlock`
(`drivers/vision/npu/core/npu-sessionmgr.c:84-109`). The existing
`npu_session_NW_CMD_POWER_NOTIFY()` holds that mutex from queueing through an
unbounded `wait_event()` on `session->nw_result`
(`drivers/vision/npu/core/npu-session.c:2916-2960`). The baseline
`npu_hwdev_normal_bootup()` acquires `vertex->lock`, increments hardware and
vertex references, then calls `POWER_NOTIFY(true)` without a complete reverse
unwind on error (`drivers/vision/npu/core/npu-vertex.c:1135-1229`). The
candidate patch replaces the raw result wait with a cookie/request-ID waiter,
adds error handling/unwind, and preserves a stack-owned publication drain.

The candidate's publication lease is in the added POWER_CTL case in
`npu-session-lifecycle-fix.patch` under `npu_protodrv_handler_nw_requested()`:
the worker begins and authorizes the waiter lease, synchronously calls
`__mbox_nw_ops_put(entry)`, then finishes the lease. Timeout can revoke a lease
before authorization. Once authorization wins, the caller waits on
`wait_for_completion(&waiter->publish_done)`; this has no timeout. Response
callbacks identify the waiter by opaque cookie plus request ID and reject
duplicates/canceled requests. Thus the response timeout bounds response
waiting only; it cannot force the publisher to progress.

In the pinned baseline, that synchronous post continues through
`nw_mbox_ops_put()` / `npu_nw_mbox_ops_put()` and the `nw_post_request` function
pointer into `nw_req_manager()`, which calls `mbx_ipc_put()`. The latter copies
the command to the mailbox ring and advances `ctrl->wptr`; the later firmware
response is a different event. `proto_drv_do_task()` invokes
`npu_protodrv_handler_nw_requested()` on the AST worker
(`npu-protodrv.c:2264-2300`). Therefore shutdown's AST `kthread_stop()` can
also wait behind a stuck synchronous post before it reaches system suspend.
This is static ordering evidence only; no bound or cancellation contract was
found for the full call chain.

The serialization evidence is limited but concrete. Normal bootup keeps
`vertex->lock` while calling `POWER_NOTIFY`; the candidate power path keeps the
session manager's `global_lock` while it waits and copies/removes the waiter.
The candidate close path marks the session closed under that same
`global_lock`. This means those same-call boot-error/close paths cannot pass
the still-blocked waiter and free its stack storage. It is not proof that
arbitrary device teardown, module unbind, or devres release is safe. Pinned
`npu_device_shutdown()` stops the protocol worker before system suspend
(`npu-device.c:783-822`); `proto_drv_close()` reaches
`auto_sleep_thread_terminate()` (`npu-protodrv.c:2920-2949`), whose helper
waits in `kthread_stop()` (`npu-util-autosleepthr.c:222-245`). That source
ordering suggests shutdown itself can also wait indefinitely for a stalled
worker, rather than cancel it. No teardown runtime test was run and no
module/device lifetime guarantee is claimed.

Separately, `npu_hwdev_bootup()` and `npu_hwdev_shutdown()` manipulate selected
`hdev->boot_cnt` and, on the non-secure path, `hdev->init_cnt` references
(`npu-hw-device.c:382-448`). These are not demonstrated module/devres pins.
The proposed detached path was not implemented, so no new reference is
acquired or released by this work. In particular, exact `hids` balance,
partial hwdev initialization failure, and whether another `boot_cnt` get can
re-enter a first-reference init callback remain unreviewed for any future
detach design.

## Actual-C host regression

`tools/hardware/test-npu-session-lifecycle.py` extracts the exact added C
helper block—from `struct npu_power_waiter` through
`npu_power_wait_cancel_and_drain()`—from the candidate patch, writes it to a
temporary include, and compiles it with
`tools/hardware/npu-power-wait-harness.c`. The harness uses pthread shims for
the Linux list, spinlock, and completion APIs used by that extracted text. It
executes these races:

* A committed publisher stalls; timeout cancellation starts and cannot
  return, the waiter remains registered, and late/duplicate callbacks are
  ignored. A delayed publisher finish releases the drain.
* A valid response arrives before publication finish; duplicate response is
  ignored, but cancellation still cannot return until the publisher finishes.
* Cancellation wins before publication authorization; authorization is
  rejected, and the failed-authorization finish path releases the drain.

Compilation and execution each have bounded subprocess timeouts. The harness
does not execute the kernel driver and does not validate IRQ behavior, Linux
memory ordering, real callback context, firmware/device state, the enclosing
session close mutex, vertex/hwdev reference counts, device teardown, module
text/devres lifetime, or mailbox MMIO. The existing Python model remains
supplemental. No private firmware or raw device trace is used.

## Readiness and next blocker

`npu-boot-preflight.py` continues to exit 2 and never authorizes BOOTUP. Its
fields separate the bounded firmware-response wait from bounded caller return,
publisher progress, retained-resource cleanup for a detached waiter, callback
lifetime, late physical power-transition safety, and device teardown pinning.
Every new lifetime/liveness/hardware field remains false. The actual-C helper
test is regression evidence, not a readiness gate and not kernel runtime
validation.

The precise next blocker is still an independently reviewed, kernel-supported
way to make a stuck publication caller return while retaining (and eventually
releasing) all state the publisher/callback/device may still touch, without
allowing unbounded retained requests. If that cannot be proved from exact
ownership and teardown paths, retain the drain and BOOTUP refusal. Even with a
memory-safe detach, late firmware POWER state and a tested device recovery
path remain separate blockers.
