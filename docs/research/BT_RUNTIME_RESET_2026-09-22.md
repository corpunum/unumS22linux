# Bluetooth normal-profile reset/readback

Accepted live boundary: firmware -> configuration -> controller reset ->
address and version readback. Linux HCI adapter registration remains separate.

The bounded trial `runtime-reset-first` ran for 4.864 seconds on recovery boot
765 without restarting the phone. All 806 patch segments and 29 NVM segments
were transferred. Standard Reset succeeded. The configured generated address
matched Read BD_ADDR, and Read Local Version returned HCI12, manufacturer29,
subversion0x687c. Bluetooth power was removed afterward with the WLAN vote
preserved. USB, model service and boot identity remained unchanged.

Source: `tools/hardware/bt-qca6490-runtime-reset.c`.
Binary SHA256: `32bfa5abc9cfecf140d1871ec543f7cd5c015752199eee844982ab99242cc4ed`.
Private receipt: `rootfs/hardware-reuse-20260921/bt-trials/runtime-reset-first/receipt.json`.

The private address uses the vendor HAL's generated fallback profile
(22:22 plus four cryptographically generated bytes), explicitly classified
`linux-generated`, not factory identity. It is ordinary Linux configuration,
not an EFS/IMEI access. Firmware payloads, generated identity and UART traces
remain excluded from GitHub. No inquiry, scanning, advertising or pairing
command was sent by this trial.

Host coverage: six runtime-NVM tests and C framing tests, including malformed
Reset opcode/status and mismatched address rejection. These cover framing and
validation, not RF operation or hardware performance.

The kernel QCA setup would repeat incompatible firmware initialization.
A userspace H4/IBS bridge to the existing kernel H4 line discipline is being
implemented and reviewed. It has not yet passed a live HCI registration test.

## Rejected HCI handoff trial

The subsequent `hci-bridge-first` trial panicked at its final read-only socket
query: `socket(AF_BLUETOOTH, SOCK_RAW | SOCK_CLOEXEC, BTPROTO_HCI)`. The captured
kernel identifies `bt_sock_create+0x144/0x150`, with `BUG_ON` at
`net/bluetooth/af_bluetooth.c:71` (`BUG_ON(!sk)`). This is
not an accepted Bluetooth adapter result. No unmodified retry is authorized by
this document; socket creation needs a source-matched kernel fix. The exact
`hci_sock_create()` body is compiled out with `#if 0` but returns success,
leaving `sock->sk` NULL. Its caller then asserts that socket state exists.
An initial suspicion about lock reclassification was corrected by reading the
numbered source; the failed assertion is the preceding NULL check.

The panic produced recovery boot766 automatically. At uptime125.19s the model,
13/13 Wi-Fi checks and1754 read-only Arch audio controls passed again. The
concurrent `audio-ctrl-progress` sample was interrupted and has no accepted
result; future hardware experiments are serialized to keep attribution clear.
No RECOVERY image or protected partition was written in this round.

Private panic capture:
`rootfs/main-driver-loop-20260921/hci-audio-panic-766/last-kmsg.bin`, SHA256
`2b0a194e7996540bd9db0a0dd0680215e25ae813f408f128903950b58676136b`.
The UART trace did not survive the panic. The supervisor now preserves partial
SSH output on host timeout; this does not reconstruct the missing earlier trace.
